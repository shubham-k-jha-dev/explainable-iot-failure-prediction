# Explainable IoT Sensor Failure Prediction using Deep Learning for Predictive Maintenance

## Overview

This project implements a predictive maintenance workflow for machine failure prediction using tabular sensor data and deep learning models. The repository focuses on predicting the binary target `Machine failure` from a set of operational features such as temperature, rotational speed, torque, and tool wear, and then explaining the model decisions using SHAP.

The project uses the AI4I 2020 Predictive Maintenance Dataset as a benchmark dataset for predictive maintenance research. The code treats it as a structured tabular dataset for model development and evaluation rather than as a live industrial telemetry stream.

Predictive maintenance aims to identify the likelihood of equipment failure before it occurs so that maintenance can be scheduled more effectively. In this project, the failure label is predicted from sensor and operating conditions. Explainability is important because it helps connect the prediction to underlying variables; a model that predicts failure but cannot explain which features contributed most is harder to trust in operational or academic settings.

This repository therefore combines:

- tabular preprocessing and feature engineering
- deep learning model training
- classification metrics and confusion matrices
- model comparison
- SHAP-based global and local explanations
- a FastAPI backend for inference and explanation endpoints

## Key Objectives

- Build a binary failure prediction pipeline for the AI4I 2020 dataset.
- Evaluate multiple deep learning architectures on the same preprocessed data.
- Compare model performance using accuracy, precision, recall, F1-score, and ROC-AUC.
- Use SHAP to interpret model behavior at both global and sample-specific levels.
- Expose prediction and explanation functionality through a FastAPI API.
- Document the full project workflow in a way that is understandable for future developers and reviewers.

## System Architecture / Pipeline

The repository implements a straightforward machine learning pipeline:

1. Dataset
   - The raw dataset is loaded from `data/ai4i2020.csv`.
   - The project uses the `Machine failure` column as the prediction target.

2. EDA
   - `src/data/eda.py` loads the dataset and reports shape, column types, missing values, duplicates, and target distribution.
   - Additional exploratory plots are generated in `reports/`.

3. Preprocessing
   - `src/preprocessing/preprocess.py` selects the relevant features and applies `ColumnTransformer` with:
     - `StandardScaler()` for numerical columns
     - `OneHotEncoder(handle_unknown="ignore", sparse_output=False)` for the categorical `Type` feature
   - It performs a stratified train/validation/test split and saves processed arrays to `models/processed_data.joblib` and the preprocessor to `models/preprocessor.joblib`.

4. Model training
   - `src/models/train_mlp.py` trains a multilayer perceptron.
   - `src/models/train_lstm.py` trains an LSTM-style model using a sequence-like reshape of the feature vector.
   - `src/models/train_cnn.py` trains a 1D convolutional model.

5. Evaluation
   - Each training script computes accuracy, precision, recall, F1-score, ROC-AUC, confusion matrix, and classification report.
   - Metrics are saved as CSV files in `reports/`.

6. Model comparison
   - `src/evaluation/compare_models.py` compares the saved metrics across MLP, LSTM, and 1D-CNN models.
   - The output is written to `reports/model_comparison.csv`.

7. SHAP explainability
   - `src/explainability/shap_explainer.py` loads the trained MLP, computes SHAP values, and exports global and local explanation artifacts.

8. API layer
   - `api/main.py` loads the trained MLP and the preprocessor and serves prediction and explanation endpoints through FastAPI.

9. Frontend
   - The `frontend/` directory exists in the repository but is currently empty; no frontend application is implemented in this codebase.

## Data Preprocessing

The preprocessing pipeline is implemented in `src/preprocessing/preprocess.py`.

### Train/validation/test split

The code uses a stratified split:

- `train_test_split(..., test_size=0.30, stratify=y, random_state=42)` for the initial split
- `train_test_split(..., test_size=0.50, stratify=y_temp, random_state=42)` for validation/test split

This results in:

- training set
- validation set
- test set

The processed data is saved in `models/processed_data.joblib` with keys:

- `X_train`
- `X_val`
- `X_test`
- `y_train`
- `y_val`
- `y_test`

### Numerical scaling and categorical encoding

The `ColumnTransformer` performs:

- `StandardScaler()` on numerical columns
- `OneHotEncoder(handle_unknown="ignore", sparse_output=False)` on the categorical column `Type`

### Class imbalance handling

The training scripts compute a positive class weight:

```python
positive_count = y_train.sum()
negative_count = len(y_train) - positive_count
pos_weight = torch.tensor([negative_count / positive_count], dtype=torch.float32)
criterion = nn.BCEWithLogitsLoss(pos_weight=pos_weight)
```

This is used in the MLP, LSTM, and 1D-CNN training scripts to reduce the bias toward the majority class during optimization.

### Other preprocessing details

- The preprocessor object is saved to `models/preprocessor.joblib`
- The selected feature list is saved to `models/feature_names.joblib`
- The processed arrays are saved to `models/processed_data.joblib`

## Deep Learning Models

### 1. MLP

The MLP is defined in `src/models/train_mlp.py` and implemented as:

```python
self.network = nn.Sequential(
    nn.Linear(input_size, 64),
    nn.ReLU(),
    nn.Dropout(0.25),
    nn.Linear(64, 32),
    nn.ReLU(),
    nn.Dropout(0.20),
    nn.Linear(32, 1)
)
```

This model uses:

- binary classification output with a single logit
- `BCEWithLogitsLoss(pos_weight=...)`
- Adam optimizer with `lr=0.001` and `weight_decay=1e-5`
- early stopping with `patience = 10`
- training for up to 100 epochs

### 2. 1D-CNN

The 1D-CNN is defined in `src/models/train_cnn.py` and implemented as:

```python
self.features = nn.Sequential(
    nn.Conv1d(1, 32, kernel_size=3, padding=1),
    nn.ReLU(),
    nn.BatchNorm1d(32),
    nn.Conv1d(32, 64, kernel_size=3, padding=1),
    nn.ReLU(),
    nn.BatchNorm1d(64),
    nn.AdaptiveAvgPool1d(1)
)

self.classifier = nn.Sequential(
    nn.Flatten(),
    nn.Linear(64, 32),
    nn.ReLU(),
    nn.Dropout(0.25),
    nn.Linear(32, 1)
)
```

The input is reshaped to a single-channel representation with `X_train_tensor = torch.tensor(X_train).unsqueeze(1)`.

### 3. LSTM

The LSTM is defined in `src/models/train_lstm.py` and implemented as:

```python
self.lstm = nn.LSTM(
    input_size=1,
    hidden_size=32,
    num_layers=2,
    batch_first=True,
    dropout=0.2
)

self.classifier = nn.Sequential(
    nn.Linear(32, 16),
    nn.ReLU(),
    nn.Dropout(0.2),
    nn.Linear(16, 1)
)
```

The input is reshaped to `(n_samples, features, 1)` before passing to the LSTM, so it is a sequence-like representation rather than a long time series of historical sensor events. The project does not construct a multi-step temporal sequence from timestamps or sensor histories.

### Why recall matters here

For failure detection, recall is particularly important because the cost of missing a failure is usually higher than the cost of a false alarm. In the project metrics, the model is evaluated as a binary classifier for failure detection, and recall measures how many actual failure cases are detected. The repository does not claim industrial deployment readiness; it uses recall as a relevant decision metric for this class-imbalanced predictive maintenance problem.

## Explainable AI

### SHAP overview

SHAP (Shapley Additive Explanations) is used to attribute model output to input features. In this project, SHAP is used to explain which features push the model toward a higher or lower failure probability. This is especially useful in predictive maintenance because the model’s decision can be inspected in terms of operational factors like temperature, torque, and tool wear.

### Global and local explanations

The project computes:

- global feature importance using mean absolute SHAP values
- local explanations for a sample prediction using the SHAP values for that instance

This is implemented in `src/explainability/shap_explainer.py`.

## Backend API

The backend is implemented with FastAPI in `api/main.py` and uses the Pydantic models in `api/schemas.py`.

### API framework and model used

- Framework: FastAPI
- Model: trained MLP
- Device: CPU (`torch.device("cpu")` in the code)

### Implemented endpoints

#### 1. Health check

- Endpoint: `GET /health`
- Response model: `HealthResponse`

Example response:

```json
{
  "status": "healthy",
  "model": "MLP",
  "device": "cpu"
}
```

#### 2. Prediction endpoint

- Endpoint: `POST /predict`
- Request model: `PredictionRequest`
- Response model: `PredictionResponse`

Request fields:

- `type`: one of `H`, `M`, or `L`
- `air_temperature`: float > 0
- `process_temperature`: float > 0
- `rotational_speed`: float > 0
- `torque`: float > 0
- `tool_wear`: float >= 0

The request is converted into a DataFrame and passed through the saved `preprocessor` before model inference.

The response includes:

- `prediction`: `0` or `1`
- `result`: `No Failure` or `Likely Failure`
- `failure_probability`: model probability of failure
- `confidence`: probability for the predicted class

#### 3. Explanation endpoint

- Endpoint: `POST /explain`
- Response model: `ExplanationResponse`

This endpoint:

- preprocesses the same input
- runs the model
- computes SHAP values for the processed input
- returns the most influential features in descending order of absolute SHAP value

Each explanation item contains:

- `feature`
- `shap_value`
- `direction`: `increases failure risk` or `decreases failure risk`

### Model loading and inference flow

The API loads:

- `models/mlp_model.pth`
- `models/preprocessor.joblib`
- `models/processed_data.joblib`

It creates a background dataset for SHAP and uses an `Explainer` over the model’s probability function. The API does not expose training endpoints or model management endpoints.

## Limitations

This project is a research-oriented deep learning workflow for a tabular predictive maintenance dataset and it has several important limitations:

- The dataset is a benchmark dataset used for experimentation in this repository; it is not described here as a live production maintenance log from an industrial system.
- The failure rate is low (3.39% in the generated EDA summary), which makes the task significantly imbalanced.
- Precision is low in the repository’s model results, which reflects the difficulty of separating the minority failure class from the majority class in an imbalanced setting.
- The models are trained and evaluated on a fixed tabular split. There is no deployment pipeline, monitoring layer, or production validation system in the repository.
- The LSTM is applied to a feature vector reshaped to a sequence-like input (`(samples, features, 1)`) rather than to a real multi-step temporal sequence. The project does not implement a true historical time-series forecasting pipeline.
- The backend API loads a single trained MLP and performs inference on a single feature vector. It is not a distributed or asynchronous inference system.
